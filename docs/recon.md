# Шаг 0 — разведка источника

Дата разведки: 1 октября 2026. Пробная выгрузка: **Тюменская область, извещения 44-ФЗ, размещённые
30.09.2026** — 112 штук, скачаны и разобраны все.

## Коротко

- **FTP ЕИС больше нет.** С 01.01.2025 выгрузка на FTP прекращена, домен `ftp.zakupki.gov.ru` не существует.
- **Раздел «Открытые данные» — тупик.** Сайт работает, но в каждом паспорте набора данных ссылка ведёт
  на тот самый FTP (`ftp://…@ftp.zakupki.gov.ru/out/published/…`).
- **Официальный машиночитаемый канал — SOAP-сервис `getDocsIP`.** Ему нужен личный токен, а портал выдачи
  токенов теперь требует **квалифицированную электронную подпись (КЭП)** — входа через Госуслуги мало.
- **Без токена работает сам сайт:** расширенный поиск фильтрует по словам (со словоформами), региону, дате,
  сумме, а по номеру закупки сайт отдаёт **полный XML извещения** — тот же документ `epNotificationEF2020`
  и т. п., что лежит в архивах SOAP.
- **Все поля из ТЗ в XML есть**, кроме одного нюанса: **ИНН заказчика напрямую не указан** — он извлекается
  из кода заказчика в ИКЗ (проверено на всех 112 извещениях).
- **Объём:** по Тюменской области 112 извещений и 8,4 МБ XML в день, по Москве — 840, по всей России — больше
  9 400. Сайт ограничивает частоту запросов (HTTP 429), поэтому скачивать нужно только подходящие закупки.

## 1. Где и в каком виде публикуются извещения

| Канал | Состояние | Что даёт |
|---|---|---|
| FTP `ftp.zakupki.gov.ru` | отключён с 01.01.2025, домен не резолвится | — |
| «Открытые данные» `/epz/opendata/` | страница жива, ссылки на наборы ведут на мёртвый FTP | — |
| SOAP `getDocsIP` | работает, нужен токен + КЭП для его получения | ZIP-архивы XML за день или за час по региону и типу документа |
| Сайт: поиск + `viewXml.html` | работает без регистрации | список закупок по фильтрам + полный XML каждой |

### SOAP `getDocsIP`

- Адрес: `https://int.zakupki.gov.ru/eis-integration/services/getDocsIP` (WSDL — `?wsdl`).
  Старый адрес `int44.zakupki.gov.ru` больше не отвечает.
- Токен передаётся в заголовке SOAP `<individualPerson_token>` и в HTTP-заголовке при скачивании архива.
  Без токена сервис отвечает `errorInfo/code = 5`, «Токены для сервисов отдачи отсутствуют в ЕИС».
- Метод `getDocsByOrgRegionRequest`: регион (2 цифры КЛАДР), подсистема `PRIZ` (извещения), тип документа
  (`epNotificationEF2020` и т. д., полный список — справочник `nsiDocumentTypes` через `getNsi`), период.
- Период — либо день (`exactDate`), либо **один час** (`oneHourInfo`: дата + час, не раньше чем через 2 часа
  после конца часа). Часовой режим придуман как раз для регулярного опроса — готовая основа для мониторинга.
- Ответ: до 1000 ссылок `archiveUrl`, либо `noData`, либо `errorInfo`.

**Получение токена.** Портал `pmd.zakupki.gov.ru` (как и личные кабинеты `lk.`) принимает только ГОСТ-TLS:
Chrome показывает `ERR_SSL_VERSION_OR_CIPHER_MISMATCH`, нужен Яндекс Браузер с включённым ГОСТ-шифрованием
и КриптоПро CSP. После этого портал открывается, но пишет: *«Для доступа в личный кабинет потребителя
машиночитаемых данных необходимо использовать квалифицированный сертификат ключа проверки электронной
подписи»*. Значит, для SOAP нужна КЭП — и каждому клиенту парсера тоже.

### Сайт ЕИС

- Поиск: `https://zakupki.gov.ru/epz/order/extendedsearch/results.html` с параметрами
  `fz44=on`, `searchString`, `morphology=on` (поиск по словоформам: «канцтовары» находит «канцтоваров»),
  `publishDateFrom/To`, `priceFromGeneral/priceToGeneral`, этапы `af` (подача заявок), `ca`, `pc`, `pa`,
  `recordsPerPage=_50`, `pageNumber`.
- **Регион:** 11-значный код КЛАДР **в обоих параметрах** — `customerPlace=72000000000&customerPlaceCodes=72000000000`.
  Старый формат с внутренним id (`customerPlace=5277335`), который встречается в чужих парсерах на GitHub,
  больше не фильтрует — сайт молча возвращает всю страну. Список из 90 регионов —
  `/epz/nsi/kladr/chooseRegion.html`.
- **Потолок выдачи:** 100 страниц × 50 = 5 000 записей на один поиск; дальше сайт повторяет последнюю страницу.
  С фильтром по региону и дате до потолка далеко (Москва — 840 в день).
- **RSS той же выдачи** (`/epz/order/extendedsearch/rss.html` с теми же параметрами) не годится как основной канал:
  отдаёт только первые 200 записей, а номер страницы и сортировку игнорирует — все «страницы» по Москве за день
  вернули одни и те же 50 записей. Проверено 3 октября 2026.
- **XML извещения:** `https://zakupki.gov.ru/epz/order/notice/printForm/viewXml.html?regNumber=<номер>` —
  `text/xml`, корневой элемент `epNotificationEF2020` / `epNotificationEZK2020` / `epNotificationEOK2020`
  (схема 16.2, пространство имён печатной формы, внутри — типы `EPtypes` те же, что в архивах SOAP).

## 2. Пробная выгрузка: Тюменская область, 30.09.2026

| Способ определения поставщика | Корневой элемент | Штук |
|---|---|---|
| Электронный аукцион | `epNotificationEF2020` | 69 |
| Запрос котировок в электронной форме | `epNotificationEZK2020` | 42 |
| Открытый конкурс в электронной форме (аудит, 307-ФЗ) | `epNotificationEOK2020` | 1 |

- Размер XML: от 17 до 877 КБ, медиана 33 КБ, всего 8,4 МБ. Большие файлы — это закупки с сотнями позиций
  и характеристиками КТРУ.
- НМЦК: от 6,8 тыс. до 94,9 млн ₽, медиана 632 тыс. ₽.
- Окно подачи заявок: от 6,6 до 19,7 дня, медиана 7,8.
- Совместные закупки: 11 из 112 извещений на несколько заказчиков (до 18).
- Изменённые извещения: 2 из 112 уже во второй редакции (`versionNumber = 2`) в день публикации.
- Количество не определено: 10 из 112 (`purchaseObjectsInfo/notDrugPurchaseObjectsInfo/quantityUndefined = true`).
  В таких закупках НМЦК — предел контракта, а в позициях цены за единицу, и суммы позиций с НМЦК не сходятся.

## 3. Структура: где какие поля

Пути одинаковы во всех трёх типах документов — **хватит одного разборщика**.

| Что | Путь (локальные имена, от корня) | Есть |
|---|---|---|
| Номер закупки | `commonInfo/purchaseNumber` | 112/112 |
| Название (объект закупки) | `commonInfo/purchaseObjectInfo` | 112/112 |
| Дата размещения | `commonInfo/publishDTInEIS` (с часовым поясом региона, `+05:00`) | 112/112 |
| Ссылка на карточку | `commonInfo/href` | 112/112 |
| Способ определения поставщика | `commonInfo/placingWay/code`, `…/name` | 112/112 |
| Электронная площадка | `commonInfo/ETP/name` | 112/112 |
| НМЦК и валюта | `notificationInfo/contractConditionsInfo/maxPriceInfo/maxPrice`, `…/currency/code` | 112/112 |
| Начало и окончание подачи заявок | `notificationInfo/procedureInfo/collectingInfo/startDT`, `…/endDT` | 112/112 |
| Заказчик — название и реестровый номер | `notificationInfo/customerRequirementsInfo/customerRequirementInfo/customer/fullName`, `…/regNum` | 112/112 |
| **ИНН заказчика** | из `…/customerRequirementInfo/contractConditionsInfo/IKZInfo/customerCode`, символы 2–11 | 111/112 |
| ИКЗ | `…/IKZInfo/purchaseCode` | 111/112 |
| Кто разместил (может быть не заказчик) | `purchaseResponsibleInfo/responsibleOrgInfo/fullName`, `…/INN`, роль — `…/responsibleRole` | 112/112 |
| Позиции: ОКПД2, КТРУ | `notificationInfo/purchaseObjectsInfo/notDrugPurchaseObjectsInfo/purchaseObject/…` (для лекарств — `drugPurchaseObjectsInfo/…`) | ОКПД2 112/112, КТРУ 75/112 |
| Место поставки | `…/deliveryPlacesInfo/byGARInfo/GARInfo/GARAddress` | 111/112 |
| Документы закупки | `attachmentsInfo/attachmentInfo` (имя, размер, ссылка на скачивание) | 112/112 |

**ИНН заказчика.** В блоке `customer` ИНН нет — только реестровый номер и название. ИНН есть у организации,
которая разместила закупку, но в 89 случаях из 112 это **не заказчик**, а уполномоченный орган
(роль `RA` — 77 раз, `ORA`, `AI`, `AU`), например «Управление государственных закупок Тюменской области».
Зато код заказчика в ИКЗ устроен как `[уровень][ИНН, 10 цифр][КПП, 9 цифр]`: `2 7202161807 720301001`.
Проверка: во всех 22 случаях, где заказчик размещал закупку сам, символы 2–11 кода совпали с его ИНН;
у всех 168 кодов ИНН начинается с 72 (Тюменская область); первая цифра — 1, 2 или 3 (федеральный, региональный,
муниципальный заказчик). Исключение — закупки без ИКЗ (в выборке одна: аудит по 307-ФЗ); для них ИНН заказчика
придётся брать иначе, если заказчик не размещал закупку сам.

**Персональные данные.** В каждом извещении есть контактное лицо: ФИО, e-mail, телефон. Сырые XML в публичный
репозиторий не кладём, тестовые файлы — только обезличенные.

## 4. Объём

| Срез (30.09.2026, 44-ФЗ, все этапы) | Извещений | XML, оценка | Скачивание через сайт, оценка |
|---|---|---|---|
| Тюменская область | 112 | 8,4 МБ (замер) | ~3 мин (замер) |
| Санкт-Петербург | 488 | ~37 МБ | ~15 мин |
| Москва | 840 | ~63 МБ | ~30 мин |
| Вся Россия | больше 9 400 | ~700 МБ | 5+ часов |

**Ограничение частоты.** Первые ~70 запросов подряд проходят, дальше сайт отвечает `429 Too Many Requests`
с `Retry-After: 5`. С соблюдением паузы вышло около 30 запросов в минуту. Ответ на каждый запрос — 0,2–0,7 с.

Вывод: «скачать всё за день по региону и отфильтровать у себя» годится для небольших регионов, но не для Москвы
и тем более не для страны. Правильный порядок — сначала сузить выдачу на стороне сайта (регион, дата, сумма,
ключевые слова), а XML скачивать только для найденного.

## 5. Сеть и сертификаты

- `zakupki.gov.ru` и `int.zakupki.gov.ru` — обычный TLS, но сертификат выдан **Russian Trusted Sub CA**
  (Минцифры), которого нет в хранилище Windows: `curl`/`requests` без настройки падают с ошибкой проверки.
  Решение — положить корневой сертификат Russian Trusted Root CA в программу и проверять по нему,
  а не отключать проверку.
- `pmd.` и `lk.` — только ГОСТ-TLS (нужны только для получения токена, парсеру не нужны).
- Всё перечисленное отвечает и через VPN с выходом в Нидерландах — исключение в VPN не понадобилось.

## 6. Что это меняет в плане

1. **Источник для v1 — сайт** (поиск + XML по номеру), а не SOAP: КЭП для токена нужна и разработчику,
   и каждому клиенту. Слой «источник» стоит сделать заменяемым, чтобы SOAP можно было подключить позже
   для тех, у кого КЭП есть, — разборщик XML останется тем же.
2. **«Архива за день» в v1 нет** — единица данных это одно извещение. Конвейер:
   поиск на сайте (регион, дата размещения, сумма, ключевые слова с `morphology=on`) → номера →
   XML каждого → локальный отбор (ключевые и минус-слова со словоформами по названию и позициям,
   ИНН заказчика из ИКЗ) → Excel → Telegram о новых.
3. **ИНН заказчика** — из `IKZInfo/customerCode`, отдельной задачей.
4. **Один разборщик** для аукционов, котировок и конкурсов — пути общие.
5. **Вежливость к сайту** обязательна с первого дня: пауза между запросами, соблюдение `Retry-After`,
   кэш скачанных XML по номеру и редакции.
6. **Мониторинг «новых»** — по номеру закупки; рост `versionNumber` означает изменение извещения.
7. **Регионы** — справочник из 90 кодов КЛАДР с сайта, коды передаются 11-значными.

## Решение по источнику

КЭП для токена получить не удалось (облачная подпись в «Госключе» не подходит: портал выбирает сертификат
из КриптоПро на компьютере). **Первая версия работает без токена — через сайт.** Модуль SOAP отложен до появления
КЭП; слой «источник» сделан так, чтобы его можно было добавить, не трогая разбор XML.

Первый прогон через сайт с паузой 2,5 с между запросами: 54 запроса подряд (поиск и 52 XML), ни одного ответа 429.
